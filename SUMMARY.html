03

Networking, as actually wired

Three address families in play, and getting a single job pod to pull from the in-cluster registry meant understanding exactly which layer resolves which one — this table is the reference that came out of that debugging.

LayerAddress spaceWho resolves itExample
Docker bridge 172.18.0.0/16 Docker's embedded DNS, host-visible server-0 → 172.18.0.3
Pod network (Flannel) 10.42.0.0/16 CoreDNS — pod-namespace only, not node-level zot-0 → 10.42.0.8
Service network 10.43.0.0/16 kube-proxy, ClusterIP-stable zot svc → 10.43.0.53 (pinned)
Host loopback 127.0.0.1 k3d's serverlb container-port mapping zot.lab.localhost:8080
The registry has two valid addresses, and that's not a bug. zot.lab.localhost:8080 resolves to 127.0.0.1 on the host — correct for docker push and CI tooling. But containerd's image-pull path runs at node-network level, outside the pod network where CoreDNS lives, so that same hostname is meaningless inside a node. The fix was pinning Zot's Service to a fixed ClusterIP (10.43.0.53) and rewriting the mirror endpoint in containerd's registries.yaml at cluster-create time.
04

The MCP servers

Two Model Context Protocol servers, both running in-cluster today — sbom-scan over streamable-HTTP, grype-mcp over stdio via kubectl exec — so the agentic layer is part of the deployable system rather than a local convenience layered on top of it.

sbom-scan 5 + 3 tools · this repo

Orchestrates Syft → Grype → Grant as one pipeline against any path, image, or archive — generates the SBOM once and reuses it for both the vulnerability and licence passes. In cluster mode (mcp.lab.localhost) it additionally exposes three tools reading the Phase 3 catalogue directly, live, over the network.

generate_sbomSyft SBOM in syft-json, spdx-json, or cyclonedx-json
scan_vulnerabilitiesGrype against a stored SBOM file
scan_targetGrype directly against an image or directory
check_licensesGrant licence compliance against an SBOM
full_scanThe whole pipeline, one call, one shared SBOM artefact
query_images_by_package in-cluster"Which running images contain this package" — live catalogue query
get_image_findings in-clusterAll current findings for one tracked image
get_catalogue_summary in-clusterAggregate counts across the whole catalogue, right now
grype-mcp 9 tools · Anchore official

The official Anchore server — broader query surface for interrogating the vulnerability database directly, not just scanning artefacts. Runs in-cluster too: its own code hardcodes stdio (no HTTP mode to enable), so it's deployed as an always-on pod and reached via kubectl exec -i instead — same protocol, the bytes just cross the Kubernetes API server rather than a local fork.

scan_dir / scan_imageDirect Grype scans, no SBOM step
scan_purlCheck one package by Package URL — pkg:npm/lodash@4.17.20
search_vulns / get_vuln_detailsQuery the Grype DB by CVE, package, or CPE
get_db_info / update_dbInspect or refresh the vulnerability database
find_grype / update_grypeLocate or install the Grype binary itself
Running today, not conceptually. Every push to this repo is gated by a real .git/hooks/pre-push hook that calls sbom-scan's full_scan before code leaves the machine. Both in-cluster endpoints answer real questions right now: a live tools/call to get_catalogue_summary through http://mcp.lab.localhost:8080/mcp returned {"images_tracked": 19, "sboms_stored": 19, "total_packages": 5099, "total_findings": 2406}, matching the numbers above exactly; and a live handshake through connect-grype-mcp.sh against the pod on agent-1 returned all 9 tools over kubectl exec -i.
No auth in front of the in-cluster endpoint yet. Anyone reachable at mcp.lab.localhost can call every tool, catalogue reads included — acceptable for a single-operator local lab, not for anything beyond it. MCPServer already accepts a token verifier for this; wiring it in is scoped out of this pass deliberately, not overlooked.

To connect a separate MCP client to the running sbom-scan endpoint (add to that client's MCP config):

{
  "mcpServers": {
    "sbom-scan-cluster": {
      "type": "http",
      "url": "http://mcp.lab.localhost:8080/mcp"
    }
  }
}

Claude Desktop reaches this the same way via a config-file entry + the mcp-remote stdio↔HTTP bridge (verified working, not the in-app "Add Connector" flow, which routes through Anthropic's cloud and can't see localhost). ChatGPT cannot reach it at all without a public HTTPS endpoint — a hard constraint on its side, no local workaround exists. Full steps: phase5-agentic/README.md.

05

Start it in three commands

Free, open source, no licence to request. Anyone with Docker and Homebrew can have the same cluster running — MCP servers included, no separate deploy step.

# toolchain: syft, grype, grant, k3d, kubectl, helm
make toolchain

# three-node cluster, storage, ingress, RBAC
make cluster

# everything else: registry, catalogue, inventory jobs,
# admission control, dashboard, and BOTH MCP servers
cd phase3-inventory && ./bootstrap.sh
