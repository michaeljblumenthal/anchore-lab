## Phase 5 pulled forward: sbom-mcp-server

Decided to build the Phase 5 agentic interface early rather than as a
throwaway "messy dependency tree" scan target for Phase 1, on the user's
suggestion. `phase5-agentic/sbom-mcp-server/` is a Python MCP server (FastMCP,
`mcp` SDK) exposing five tools: `generate_sbom` (Syft), `scan_vulnerabilities`
(Grype on a stored SBOM), `scan_target` (Grype direct), `check_licenses`
(Grant), and `full_scan` which chains all three, reusing one SBOM artefact for
both downstream steps — the "SBOM is the unit of work" principle from the plan
enforced in code, not just as a scanning habit.

This project's own `pyproject.toml` (mcp SDK, pydantic, jsonschema,
cryptography, PyJWT, starlette/uvicorn for transport) is itself a real,
messy-enough Python dependency tree — 27 resolved packages
(`requirements-freeze.txt`) — so it doubles as the Phase 1 "real application"
target instead of a synthetic LangGraph stub.

Registered as a project-scoped MCP server via `.mcp.json` at the repo root so
Claude Code (or any MCP client opening this project) can call it directly.

**Two real findings while building it, both worth keeping for the write-up:**

1. Grant's default policy denies everything, including permissive licences
   like MIT/BSD-3-Clause, because the default policy has an empty allow-list
   rather than an empty deny-list. First-run output looks like "the whole
   project is noncompliant" until you understand you need to author a
   `grant.yaml` policy. Confirmed with a real run against the server's own
   SBOM: 75 packages catalogued, 36 with a real licence got "denied" purely
   on default policy, 2 unlicensed.
2. `grant` installed via Anchore's own `install.sh` script into `~/bin`,
   which only resolves on PATH in an interactive shell that sources
   `~/.zshrc` — a bare subprocess (like this MCP server, or a CI runner)
   won't see it. Fixed with a symlink into `/opt/homebrew/bin`. Small thing,
   but it's exactly the kind of packaging gap that bites automation and not
   humans.

Verified end to end: `full_scan("dir:.")` against the server's own venv
produced a 75-package SBOM, 0 Grype matches, and a real Grant compliance
report — full pipeline working via direct Python calls (not yet exercised
through an actual MCP client round-trip).

## Phase 2: Kubernetes cluster

Built the three-part structure up front this time: `phase2-cluster/bootstrap.sh`,
`make cluster` / `make clean-cluster`, `phase2-cluster/README.md` checklist.

Cluster: k3d, 1 server + 2 agents (all Docker containers inside the Colima
VM), k3d's default Traefik ingress kept rather than swapping in
ingress-nginx — no reason to add the extra moving part when Traefik ships
already wired to k3d's load balancer. Namespaces `anchore-lab` (workloads)
and `anchore-lab-system` (reserved for Phase 3's Harbor/MinIO/Postgres/jobs).
RBAC: a `lab-workload` ServiceAccount bound to a namespaced Role (not
ClusterRole), scoped only to what's needed today — explicitly not granting
cluster-wide image-listing access yet, since that's a Phase 3 need and
should be added when Phase 3 actually needs it, not speculatively now.

Came up clean on the first `k3d cluster create`, all 3 nodes Ready. Storage
and ingress both needed a genuine diagnose-and-fix pass, which is exactly
what the plan asks for:

**PVC stuck Pending.** First attempt applied a bare PVC and waited for
`Bound` — it never arrived. `kubectl describe pvc` showed the real story
immediately: `local-path`'s `VolumeBindingMode: WaitForFirstConsumer` means
the provisioner correctly waits to know which node needs the volume before
creating anything. A PVC with no consumer is not a bug in the storage class,
it's an incomplete test. Fixed by adding a pod that mounts the PVC; bound in
~2 seconds once a consumer existed.

**Ingress hostname needed no DNS setup.** Expected `lab.localhost` to need
an `/etc/hosts` entry and wrote the bootstrap script assuming so. It didn't:
macOS resolves the entire `.localhost` TLD to 127.0.0.1 automatically
(RFC 6761), confirmed via `dscacheutil` and a real ping, not just a Host
header trick. Corrected the script's echoed guidance, which had wrongly
claimed a hosts-file edit was required. Flagged as possibly
platform-specific — worth a footnote if this lab ever gets rebuilt on Linux,
where the same guarantee depends on nsswitch/systemd-resolved config rather
than being universal.

**CrashLoopBackOff vs. CreateContainerConfigError.** The plan names
`CrashLoopBackOff` from a malformed secret as the deliberate-breakage
example. Reproducing it literally (`envFrom.secretRef` pointing at a
nonexistent Secret) instead produced `CreateContainerConfigError` — the
kubelet refuses to start the container at all when it can't resolve an env
source, so there's no process to crash and no restart loop. Had to
reproduce actual `CrashLoopBackOff` separately with a container that starts
and then exits nonzero (`sleep 2; exit 1` under `restart: Always`),
confirmed via the `BackOff: Back-off restarting failed container` event and
a climbing restart count. This distinction is worth keeping for the
write-up as its own finding: two commonly-conflated pod failure states with
different causes and different fixes, and a support engineer needs to tell
them apart at a glance rather than treating "the pod is broken" as one bucket.

Verified end to end: `make cluster` from repo root reproduces the exact same
cluster/namespace/RBAC/PVC/ingress result as running `bootstrap.sh` directly,
confirmed by a full idempotent re-run (cluster reused, all manifests
unchanged/reconciled, storage and ingress both still working).

## Phase 3: the substance of the lab, and where nearly all of today's real findings live

This was the longest, most iterative segment of the build. Full detail is
in `phase3-inventory/README.md` (9 numbered findings); this is the
narrative version.

**Registry: started with Harbor, ended with Zot.** Harbor's official images
are amd64-only — no arm64 manifest — and crash with a Go nil-pointer panic
when run emulated under QEMU on this Mac's arm64 k3d nodes. Tried forcing
the whole cluster to amd64 (`DOCKER_DEFAULT_PLATFORM`, Colima
`--vz-rosetta`); k3d has no mechanism to honour either, nodes stayed arm64
regardless. Switched to Zot, a genuinely multi-arch OCI registry, at the
cost of Harbor's UI/project/RBAC layer (unused by this lab anyway). This is
arguably the single most quotable finding from today: a customer evaluating
this exact open-source stack on an M-series Mac hits a wall before any
Anchore tooling is even involved.

**Then `docker push` itself turned out to be unreliable.** Against Zot,
`docker push` always attempted HTTPS and failed, despite `docker info`
correctly listing the registry under Insecure Registries, despite a
confirmed-working plain-HTTP endpoint (curl), and despite retrying against
a bare IP to rule out DNS. This looks like a genuine Docker registry-client
bug/quirk under Colima, not a config mistake. Routed around it with
`crane push --insecure` instead — except `crane push` on a `docker save`
tarball got `MANIFEST_INVALID` from Zot (docker-schema2 vs. the OCI format
Zot expects), so images built locally in this repo now go through
`docker buildx build --output type=oci` (needed installing the
`docker-buildx` Homebrew formula and pointing `~/.docker/config.json` at
its `cliPluginsExtraDirs`) before `crane push`. Two scripts came out of
this: `push-to-registry.sh` (local Dockerfile builds) and
`mirror-to-registry.sh` (upstream image pulls) — deliberately separate,
since the two paths produce genuinely different artefact formats.

**Bitnami quietly pulled its free-tier images from Docker Hub (Aug 2025).**
`bitnami/minio` 404'd entirely, not just the pinned tag — the whole
repository moved behind a paid tier, leaving only the unsupported
`bitnamilegacy/*` mirror. `bitnami/postgresql` still resolves under
`:latest`, inconsistently. Repointed both MinIO's main and console images
at `bitnamilegacy/*`. Worth its own line in the write-up: a supply-chain
break that has nothing to do with vulnerability content, purely a vendor
pulling a repository out from under a pinned Helm chart.

**Getting a pod to actually pull from the in-cluster registry took three
more distinct fixes, each a different layer of the same "host address vs.
in-cluster address" problem:**
1. containerd on every node needed `registries.yaml` (passed to k3d via
   `--registry-config`, baked in at cluster-create time only) telling it
   the registry is insecure — same class of problem as the Docker daemon.
2. The mirror endpoint in that file can't be the registry's Kubernetes
   Service *DNS name*: containerd's pull path runs at the node/host network
   level, outside the pod network where CoreDNS is reachable, so
   `zot.anchore-lab-system.svc.cluster.local` gave NXDOMAIN. Had to use the
   Service's ClusterIP directly (confirmed reachable from node network
   namespaces even though DNS isn't) — and since that address is needed
   *before* Zot is even installed, pinned Zot's Service to a fixed
   ClusterIP (`10.43.0.53`) in its Helm values rather than trying to
   sequence around the chicken-and-egg problem.
3. `sbom_generate.py` calls Syft directly (not via containerd), so it hit
   the same translation problem a third time — needed its own rewrite from
   the catalogue's stored `zot.lab.localhost:8080` references to the
   in-cluster form — and then Syft's own HTTP/TLS insecure-registry default
   a fourth time (`SYFT_REGISTRY_INSECURE_USE_HTTP`,
   `..._SKIP_TLS_VERIFY`). Four different tools (Docker CLI, containerd,
   Syft, and implicitly Grype) each needed their own separate
   insecure-registry opt-in for one plain-HTTP registry — there is no
   single setting that covers this across a toolchain.

**k3d's own loadbalancer container intermittently failed to boot** —
`confd: FATAL stat /etc/confd/values.yaml: no such file or directory` in a
tight retry loop, roughly half the `k3d cluster create` runs this session
(with and without `--registry-config`, so unrelated to that flag). No root
cause found; `k3d cluster delete` + recreate is the only reliable recovery.
Baked an automatic retry-with-delete-on-failure loop into
`phase2-cluster/bootstrap.sh` so this doesn't need to be caught by hand
every time. Practical lesson: `k3d cluster create --wait` succeeding, or
even `kubectl get nodes` showing Ready, does not guarantee the loadbalancer
that owns all ingress traffic is actually up — always check
`docker ps` for the serverlb container's real state.

**Once all of the above was fixed, the core pipeline ran clean and
produced real numbers.** Runtime inventory found 11 distinct images across
the cluster on first run. SBOM generation covered all 11 (10/11 on the
first pass — the lab's own `runtime-inventory` image was the one still
tripping the registry-addressing bug, fixed as above). The re-matching job
— the plan's central measurable claim — refreshed the Grype DB in 34.8s
and then re-matched all 11 stored SBOMs in 16.8s, reading 20MB from MinIO,
pulling zero images. Total findings across the 11 images: 1,604 (124
Critical, 672 High) — already a real, publishable instance of "the number
is too large to read by hand, which is the argument for a queryable
catalogue instead of a report."

**Kyverno's audit-mode policies caught a real self-inflicted violation
immediately**: the `catalogue-schema` Job's `postgres:16-alpine` image (no
explicit registry prefix, which Docker/K8s resolve to
`docker.io/library/postgres` implicitly, not matching the policy's explicit
`docker.io/*` glob) and its lack of resource limits, both genuine bugs in
this repo's own manifest. Left both in place rather than quietly patching
them — this is exactly the "the stack fails its own policy" finding Phase 6
predicts, arriving three phases early, and it's more honest to record it as
found than to fix it silently before anyone sees the audit report.

## Phase 6: turn the system on itself

Deliberately extended the existing Phase 3 pipeline to cover itself rather
than building a separate one-off scanner, per the plan's "nothing gets an
exemption on the grounds that it is infrastructure" instruction — a
special code path for the self-scan would itself have been a kind of

**Coverage: 19 images, 19 SBOMs, 0 gaps** — every namespace, k3s system
components and Kyverno's own four controllers included.
**5,099 packages catalogued, 2,406 findings before triage** (185 Critical,
1,012 High) — the plan's predicted headline number, now a real one.
Continuous re-matching held at this scale too: 35.1s DB refresh + 30.4s to
re-match all 19 SBOMs, 30MB read, zero re-pulls.

accounts for 573 findings on its own — about a quarter of the entire

Ran a full cluster-wide Kyverno audit: 64 pass, 8 fail on the first pass,
